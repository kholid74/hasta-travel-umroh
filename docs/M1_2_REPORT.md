# M1.2 Financial Documents

Visual refinement M1.2B replaces the original plain layout and standard Helvetica with branded tables, logo and embedded Lato. See [M1.2B report and current samples](M1_2B_REPORT.md); the implementation history below describes the original M1.2 delivery.

## Implemented

Invoice, payment receipt and Statement of Account share `lib/admin/financial-documents.ts`. They generate actual A4 PDF files using pdf-lib, with dark green/gold Hasta identity, deterministic DEMO identifiers, repeated headers/footers, wrapping and automatic pagination. All issuer details explicitly describe a fictional showcase; no official numbers, legal/tax identity or compliance claims are introduced.

`FinancialDocuments.tsx` previews the exact PDF Blob exported by its download link. Open an existing booking/invoice, select Pratinjau Invoice or Pratinjau Statement of Account. Lihat pembayaran moves to transaction history. Each eligible verified transaction has Pratinjau Kuitansi Pembayaran; pending rows retain verification and show a disabled receipt with its reason. Downloads are available inside previews, including on mobile browsers without an embedded PDF viewer.

Invoice and statement read saved booking amounts and only verified payments. One bigint balance helper also supplies existing paid/outstanding functions; negative balances are no longer silently clamped. Inconsistent contracts block documents with an explanation. Cancellation/return/status changes invalidate live previews and receipt eligibility. PDFs never mutate state or include HPP.

New bookings snapshot their package description; existing contracts retain their exact amount and explicitly label the current-description fallback when a historical name is unavailable. Haji uses its own package association, never a fabricated Umrah departure. Original currency assumptions remain visible. Verification now records an optional timestamp; historical transactions without one are labeled as unknown, separately from transaction dates. Optional payment references are included when present. Optional fields persist through the existing versioned storage without resetting M1.1 data.

Invoice includes a single package charge because existing contracts have no itemized charge records. Due dates appear only when configured. Bank instructions appear only when bank/account are configured and are explicitly labeled demo. Statement payments sort by transaction date then reference; generated date is shown. Receipt eligibility is checked again during generation.

## Limitations

- Files are browser-generated snapshots, not signed tax documents. Previously downloaded files cannot be revoked; every PDF directs the reader to the current workspace status. Live preview URLs are revoked when closed or state changes.
- Standard PDF Helvetica supports Latin/WinAnsi characters. Unsupported scripts produce an explicit generation error; no text is silently substituted. Custom multilingual font embedding is not included.
- Built-in browser PDF viewer availability varies; the identical PDF download remains available on mobile. Preview and exported text were inspected in Chrome.
- Storage remains local to this browser/origin. No server ledger, cross-tab synchronization, official numbering, tax calculations, signatures or bank reconciliation are added.
- Legacy descriptions and verification dates cannot be reconstructed. Contract totals are never inferred from current package prices. Invoice issue date uses saved booking date; document generation date is separate.
- npm installation reported 21 audit findings in the dependency tree (16 moderate, 4 high, 1 critical). Framework/dependency remediation outside this milestone was not applied; no automatic breaking upgrades were run.
